# Contributing

## Setup

```bash
uv sync
uv run pytest -q
```

## Gates

All three must pass before a change lands:

```bash
uv run pytest -q
uv run ruff check . && uv run ruff format --check .
uv run ty check src tests scripts
```

`server/.agents/`, `server/project.py` and `server/__init__.py` are excluded from linting: they are
generated by `maltego-transforms start server --with-skills` and treated as upstream-owned, so
linting them would churn against regeneration. The rest of `server/` — `transforms/`,
`middleware.py`, `discovery.py` — is this project's code and is linted, including anything
`scaffold` generates, so the generator's output has to pass the same gates as hand-written code.

## Scope

This project exists to help an agent **author transforms and prove they work**: the scaffolder
(`src/transformatron/scaffold/`) produces a first draft from a cURL command or an OpenAPI spec, and
the server lifecycle and transform execution close the loop — restart, run, count the entities,
correct the mapping. Changes that make that loop faster or more honest are in scope.

General SDK guidance — entity selection, settings, pagination, TRX migration — is not. It ships with
the `maltego-transforms` SDK in `server/.agents/skills/`, and a copy here would go stale against
the package, so it is deliberately not duplicated — with one exception, below.

Also out of scope by decision: web dashboards, databases, deployment tooling, and any multi-server
registry. The model is one local server hosting many transform modules.

## Where corrections to SDK guidance live

`docs/transform-authoring.md` contradicts the shipped SDK skills on two points. That is
deliberate, and the placement matters:

- **Do not fix the skill files in `server/.agents/skills/`.** They are regenerated by
  `maltego-transforms start server --with-skills`, which silently reverts edits.
- **Do not patch `.venv/lib/.../maltego/`.** It is an installed dependency; the next `uv sync`
  reverts it, and the patch would diverge from what every other user runs.

So corrections live in `docs/`, which nothing regenerates. `docs/upstream-sdk-issue.md` is a
prepared bug report — the durable fix is upstream, and if it lands, the correction in
`docs/transform-authoring.md` can be removed.

## Two front ends, one implementation

The MCP tools (`src/transformatron/mcp.py`) and the CLI (`scripts/transformatron_cli.py`) are both
thin shells over `src/transformatron/operations.py`. This keeps the project usable by agents that
speak MCP, agents that only run shell commands, and humans, without three copies of the behaviour.

**Add operations to `operations.py`, not to a front end.** A tool or subcommand should be a couple
of lines that delegates.

Agent guidance follows the same single-source rule: `AGENTS.md` is canonical (the convention Codex
and Gemini CLI read), and `CLAUDE.md` points at it rather than restating it.

## Protocol facts that shaped the code

Non-obvious behaviours of the Maltego v3 protocol, each of which cost real debugging time. Read
these before changing `client.py`.

- **Two success states.** A run ends `COMPLETED` *or* `FINISHED`; both mean success. The server
  reports `state: "COMPLETED"` while its own status text says `ExecutionState.FINISHED`. Handling
  only one hangs the poll loop.
- **Results are events, not entities.** `result.events[].data` carries an `inputType` of
  `ENTITY`, `LINK`, or `STATUS_MESSAGE`. The full list is **replayed on every poll**, so the client
  must track an offset or entities double-count.
- **`status` is an object**, not a string. The run id is at `result.runId`.
- **Transform ids are fully qualified** — `acme.new_maltego_integration.my_transform`, the `name`
  field from `GET /api/v3/transforms`, not the Python function name.
- **Env vars beat explicit kwargs.** `ServerHTTPSettings` is a pydantic `BaseSettings`, so
  `MALTEGO_SERVER_*` variables override values hardcoded in `project.py`. That is how the lifecycle
  tools set host, port, and scheme without editing the user's project file. `project.py` parses no
  CLI arguments, so flags passed to it are silently ignored.

## SDK behaviours worth knowing

- **A `MaltegoGraph` returned from a plain `async` transform is silently discarded** — zero
  entities, run still reports success. In `__handle_async_result`, a returned graph fails both
  `isinstance` branches and falls through. Return a list instead; a union return annotation
  (`-> list[AS | ISP]`) still publishes every output type to discovery. This contradicts the SDK's
  own `maltego-transform-build` skill, whose `return graph` example holds only for async
  *generators*.
- **The Maltego desktop client refuses plain-HTTP transform servers.** The rejection happens
  client-side, so no request reaches the server and nothing appears in the log. An empty log next
  to a client-side error is the signature.

## Design decisions

Reasoning behind choices that look arbitrary but are not:

- **Zombie reaping in `lifecycle.py`.** Stops originally took 10.2s, always falling through to
  SIGKILL. The `Popen` child was never reaped, so it lingered as a zombie and `os.kill(pid, 0)`
  kept reporting it alive. `_OWNED` tracks handles so liveness comes from `poll()`. Shutdown is now
  0.4s. Do not remove that dict without re-testing stop timing.

- **The server scheme is recorded in `.transformatron/server.scheme`.** `project.py` defaults to
  `https`, but the lifecycle tools override the scheme per start, so a server may be serving either.
  Without the recorded scheme the health probe polls the wrong one and a healthy server looks
  unreachable.

- **`generate_certs` prints the trust command rather than running it.** Trusting a certificate
  changes system-wide trust, which is the user's decision to make.

- **`.mcp.json` passes no `--directory`.** It previously used `--directory "${PWD}"`, assuming
  Claude Code expands `${PWD}` at config-load time. It does expand `${VAR}` from the environment,
  but `PWD` is not reliably set for the spawned process, so the argument could reach `uv` literally
  and fail on a directory named `${PWD}`. The flag is unnecessary — `uv run` walks up from the
  working directory to find the project root. Do not reintroduce it.

- **A stale MCP process is documented, not detected in code.** The MCP server imports
  `src/transformatron/` once at startup, so edits to this package do not reach the running tools.
  It cost two debugging sessions: a false "did not answer" from `server_restart` after the fix had
  landed, and MCP tools probing `http://` against an HTTPS server while `68ec099` was being
  written. Both times MCP and the CLI disagreed and the CLI was right.

  Configuration is the exception, deliberately: every tool loads the config on each call rather
  than sharing one built at import, so an edit to `transformatron.toml` applies on the next call
  and a broken file comes back as a tool result instead of stopping the MCP server loading.

  A runtime check is possible — the package is installed editable, so each loaded `transformatron`
  module can be hashed on disk and compared against what was imported. It was deliberately not
  built: that adds a check on every tool call to report something a reader can be told once. The
  warning lives in `AGENTS.md` instead. If you later decide the check is worth it, that is the
  mechanism.

## Testing

Test behaviour and edges, not implementation. Mock only slow, non-deterministic, or external
boundaries — the transform server subprocess and upstream HTTP APIs qualify; internal functions do
not.

**Break the code to verify the test catches it.** Four behaviours in the lifecycle and client were
mutation-tested this way — dropping `FINISHED` from the success states, removing event
de-duplication, removing timeout-cancel, and removing zombie reaping — and each was caught by
exactly the intended test. The HTTPS scheme resolution was verified the same way. If you add a
regression test, confirm it fails against the bug before you call it done.

## Known gaps

Honest about what has not been exercised:

- Verified on macOS only. Linux should work but is untested; the certificate trust command in the
  README is macOS-specific.
- Windows is not supported. `_pid_is_alive` probes with `os.kill(pid, 0)`, which on Windows
  terminates the process instead of testing it, and `stop` relies on `SIGKILL`, which Windows does
  not define.
- Cert trust has not been exercised against the Maltego Graph Browser, only that HTTPS serves.
- Binding a non-loopback `host` makes the server reachable from other machines, but the generated
  certificate covers only `localhost` and `127.0.0.1`, and the seed URL shows the bind address —
  `0.0.0.0` is not something a remote client can dial. A remote client needs the machine's real
  address and a certificate that covers it.
