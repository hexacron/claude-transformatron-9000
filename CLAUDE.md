# claude-transformatron-9000

Build and manage Maltego v3 transforms against a locally hosted transform server.

## Division of labour — read this first

Two layers, and they do not overlap:

| Need | Use |
|------|-----|
| **Write or change transform code** | The official SDK agent skills in `server/.agents/skills/` |
| **Run, reload, or inspect the server** | The `transformatron` MCP tools |

**To author a transform, load `server/.agents/skills/maltego-transform-skill-index/SKILL.md`
first.** It is a routing table that points to the one focused skill for the task
(`maltego-transform-build`, `-design`, `-test`, `-discover`, `-docs`, or the TRX migration pair).
Load one skill at a time; load its `references/` only when the task needs them.

These skills ship with `maltego-transforms` and are versioned with the SDK. Do not re-derive SDK
APIs from memory and do not duplicate this guidance here — it goes stale.

## MCP tools

- `server_start(ssl=False)` / `server_stop()` / `server_restart(ssl=False)`
- `server_status()` — running, healthy, transform count
- `server_logs(lines=50)` — first place to look when a transform fails to register
- `list_transforms()` / `get_transform(id)` / `list_entities()`
- `run_transform(transform_id, entity_type, entity_value, settings=None, timeout=60)`
- `get_seed_url()` — the URL to register in the Maltego client
- `generate_certs(force=False)` — self-signed cert for HTTPS

## The loop

1. Add or edit a module under `server/transforms/`.
2. Import it in `server/project.py` (`from transforms.my_module import *`) — the server only
   discovers what `project.py` imports.
3. `server_restart` — this is the reload path.
4. `list_transforms` to confirm it registered, then `run_transform` to exercise it.

If a transform is missing from `list_transforms`, or shows an output type of `NONE`, the cause is
almost always a missing or untyped annotation. Input type comes from the parameter annotation and
output type from the return annotation; a bare `-> list` advertises no output type and breaks
client routing.

**Never return a `MaltegoGraph` from a plain `async` transform.** It silently yields zero entities
while the run still reports success: in the SDK's `__handle_async_result`, a returned graph fails
both `isinstance` branches and is dropped. Return a list — `-> list[AS | ISP]` still publishes
every output type to discovery. This contradicts the SDK's own `maltego-transform-build` skill,
whose `return graph` example only holds for async *generators*.

## Layout

- `server/` — the transform server, generated by `maltego-transforms start server --with-skills`.
  Treat as SDK-owned; it is excluded from our lint config.
  - `server/transforms/examples/` — illustrative samples, not maintained integrations. Users are
    expected to delete them; do not build on them or treat their API as stable.
- `src/transformatron/` — the MCP control plane (`config`, `client`, `lifecycle`, `certs`, `mcp`).
- `.transformatron/` — runtime state: PID file, server log, generated certs. Not checked in.

This is a public repository: `README.md` is the user-facing entry point. Keep setup instructions
there and agent-facing guidance here rather than duplicating between the two.

## Notes

- The server runs on port **3000**. The SDK's own skill scripts default to 8080 — pass
  `--port 3000` if you invoke them directly.
- The server is steered by `MALTEGO_SERVER_*` environment variables, which take precedence over
  the values hardcoded in `project.py`. That is how the lifecycle tools set host, port, and scheme
  without editing the project file.
- **HTTPS is required by the Maltego desktop client too, not just the Graph Browser.** The desktop
  app refuses plain HTTP outright ("Only HTTPS (SSL/TLS) Transform Servers are allowed") and never
  sends the request, so nothing appears in the server log. Run `generate_certs`, then
  `server_restart(ssl=True)`, and register the `https://` seed URL. Trusting the generated cert
  changes system trust, so `generate_certs` prints the `security add-trusted-cert` command instead
  of running it.
- The scheme a running server was started with is recorded in `.transformatron/server.scheme`.
  `project.py` hardcodes `http`, so that file is the only way the control plane knows to address
  a `ssl=True` server over HTTPS.
